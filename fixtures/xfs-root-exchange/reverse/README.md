# Reverse existing-name exchange

The same pinned Linux 6.12.107 reference operation exchanged the two names
again after the forward image had been recovered and cleanly unmounted.
The dirty root still has the exchanged mapping; the sole live transaction
at LSN (1,19) restores hello=inode99/64 bytes and pattern=inode100/9001 bytes.
It is again one root CORE|DDATA item, with no allocation or regular-file
inode/data changes. Linux recovery produced `root-after.hex` and passed
`xfs_repair -n`. The original mounted readers retained their inode identities.

This direction lets the existing process fixture's ordinary read clients
verify the recovered bytes without different programs or a kernel mode.
The live log starts at LBA 524328, tail19/head21; completion is body524350
then header524349. The private process runner expects root96 plus those two
completion sectors, with three writes and three Flushes. Its completed-command
interruption gates use the same existing four cut selectors.

The captured superblock, recovered root and complete dirty image hashes are
in `hashes.json`. These are independent Linux inputs/outputs, not values
generated by the Aurora implementation. Read-only and refused images must
remain byte-identical. This establishes no physical power-loss behavior.

`dirty.img.xz` is the genuine Linux dirty input. `completed.img.xz` is a
frozen recovery-plan completion, independently mounted by Linux without log
replay, with exact file hashes and a passing `xfs_repair -n`. It is not the
Linux post-unmount whole image and must not be regenerated from the current
implementation as its own oracle. The root sector itself is compared against
actual Linux replay output. Decompress both archives to fresh private paths
with `xz -dc` and verify the raw SHA-256 values in `hashes.json`; pass the
completed image as `--recovery-reference` for each cut-prefix comparison.
